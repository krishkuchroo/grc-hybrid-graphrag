# S3 demo: uploads, import mapping, evidence, audit findings and the generators

The click-through for S3's part of the checkpoint (D114, D182). Follow these steps while recording
the walkthrough with the Mac's screen recorder (D115).

## Before you start

- The one-time setup is done (D65): Caddy's local certificate is trusted, and the hosts file has
  `127.0.0.1 grc.localhost`.
- The stack is running, the worker included (it reads and imports asset lists):
  `docker compose -f packages/infra/compose.yaml --env-file .env up -d`.
- The demo logins and data exist. They come from `pnpm seed:demo`, which creates two orgs, Acme
  Corp (`@acme.example`) and Globex Ltd (`@globex.example`), with one user per role, each org's own
  records (`docs/demo/s1.md`) and framework mappings (`docs/demo/s2.md`). For S3 it also gives each
  org, through the same services the app uses, so every change is in the audit trail:
  - an asset list, a CMDB export uploaded from the source `demo-cmdb` and imported with a column
    mapping that is saved for that source: 8 new assets, linked by what hosts and runs what;
  - two policy documents and one SOC ticket file, uploaded and waiting for processing;
  - evidence on two controls: on the Control Owner's Multi-factor sign-in control (Acme) or Mobile
    device management control (Globex), one item the Control Owner added and one the Admin added,
    the Admin's expiring within 30 days; and one item on a control another person owns;
  - three audit findings added by the Auditor, each concerning a control or a risk: one open and
    overdue, one risk accepted, one closed.

  It prints the login list. Running it again adds nothing.

- Every demo login uses the same password: the `DEMO_USER_PASSWORD` value in `.env`. It is never
  written here or printed.
- Have an authenticator app on your phone ready. The first sign-in of each login asks you to set up
  two-factor sign-in, as in the M0 demo (`docs/demo/m0.md`, steps 3 to 6).
- The files to upload during the walkthrough are in `packages/infra/scripts/demo-intake/walkthrough/`.
  The seed never uploads them. A file is stored once per org, so after a first walkthrough the
  first upload of each of them already shows the repeat notice.

The logins used below:

| Login                         | Role          | Clearance    |
| ----------------------------- | ------------- | ------------ |
| `risk.manager@acme.example`   | Risk Manager  | confidential |
| `control.owner@acme.example`  | Control Owner | internal     |
| `auditor@acme.example`        | Auditor       | confidential |

## Steps

1. Open https://grc.localhost and sign in as the Risk Manager, `risk.manager@acme.example`, with the demo password.
2. In the left navigation, under Data, open Data intake. The Uploaded documents list shows the seeded files: `acme-cmdb-export.csv` (Asset list, from demo-cmdb, Imported), the policy documents `acme-acceptable-use-standard.txt` and `acme-incident-response-plan.txt`, and the SOC ticket file `acme-soc-tickets-2026-09.json`, each Stored and waiting for processing.
3. Upload a policy document. In "Upload a file", choose Policy document, leave the label at Internal, press Choose a file and pick `walkthrough/acme-remote-working-policy.txt`, then press Upload. The notice reads "Uploaded acme-remote-working-policy.txt": it is stored and queued for processing, and it appears, highlighted, in the list below.
4. Upload the same file again: choose Policy document, pick `acme-remote-working-policy.txt` again and press Upload. This time the notice reads "Already uploaded": the file was already uploaded on today's date, and nothing new was stored. A file is identified by its contents, so a repeat upload stores nothing and queues nothing; the audit trail still records the attempt.
5. Upload an asset list from a new source. Choose Asset list, type `Lansweeper` in Source system, pick `walkthrough/acme-lansweeper-leeds-1.csv` and press Upload. The notice says its columns are being read; press Open the import.
6. The import page reads the file, then shows "Match the file’s columns to asset fields", with the file's sample rows. Some fields are suggested from the column names (Criticality from Tier, Data classification from Classification, Owner (email) from Managed By, Hosted on from Hosted On). Choose the rest: Source ID is Asset Tag, Name is Device Name and Asset type is Kind. Leave "Save this mapping for Lansweeper" ticked and press Run import.
7. The import is queued, then runs in the worker, then shows its results: Added 4, Updated 0, Unchanged 0, Failed 0, Links added 2, and "Every row was imported without a problem."
8. Open Assets in the left navigation. The new assets are in the list: Branch hypervisor (Leeds), Branch file server (Leeds), Print server (Leeds) and Branch router (Leeds), each with its own number. Open Branch hypervisor (Leeds): its dependency map shows it hosting the file server and the print server. The seeded CMDB assets are there too: open Order service to see it hosted on App server prod-01 and run by the Kubernetes platform.
9. Go back to Data intake and upload a second list from the same source: choose Asset list, type `Lansweeper` again (the same spelling), pick `walkthrough/acme-lansweeper-leeds-2.csv` and press Upload, then Open the import. There is no mapping step this time: the source's saved mapping fits the file's columns, so the import starts by itself and finishes with Added 1 (Branch Wi-Fi controller (Leeds)), Updated 1 (Print server (Leeds), whose tier changed from Low to Medium) and Unchanged 3. Rows from the same source update the same assets instead of adding copies.
10. Download a document. In the Uploaded documents list, press the Download button on the row of `acme-incident-response-plan.txt`. The browser saves the file. Downloads go only through the app, which checks the role and the label first, and each one is recorded in the audit trail.
11. Sign out, and sign in as the Control Owner, `control.owner@acme.example`. Open Data intake: "You don’t have access to Data intake". A Control Owner uploads nothing there; the page points to Controls, where evidence for their own controls is added.
12. Open Controls, then Multi-factor sign-in for remote access, one of the controls they own. Its Evidence section lists two items: "MFA enrolment report, September 2026", which they added, with its Edit and Retire buttons; and "VPN gateway MFA settings export", which the Admin added, marked Expiring soon, with only its Download button: a Control Owner sees all the evidence on their own controls but changes only what they added themselves. Its Audit findings section shows the open finding about contractor VPN accounts, marked Overdue.
13. Add evidence to this control as the Control Owner. Press Add evidence, type the name `Remote access MFA review, Q3 2026`, set Collected to 30 September 2026, leave Valid until empty, keep the label at Internal, pick `walkthrough/acme-mfa-access-review-q3.txt` and press Add evidence. The new item appears in the list with its own evidence number, Pending review, and with Edit and Retire buttons, because they added it.
14. Sign out, and sign in as the Auditor, `auditor@acme.example`. Open Data intake: "You don’t have access to Data intake". Auditors read the records and add audit findings, but upload no files.
15. Add an audit finding from a control page. Open Controls, then Monthly patching. In its Audit findings section press Add audit finding. Fill in the form: title `Patching window missed for two branch servers`, severity Medium, status Open, date identified today, a due date a month from now, source or audit reference `Acme internal audit IA-2026-10, item 1`, a root cause and a remediation plan in a sentence each, the owner Control Owner (Acme Corp), label Internal. Press Add audit finding. The section lists the new finding, and the confirmation names its number: "AUD… was added and concerns this control."
16. Click the number in the confirmation to open the finding's page. It shows every field, its remediation, and the control it concerns, Monthly patching. Copy the page's address for step 20.
17. Add an audit finding from a risk page. Open the Risk register, then Phishing of staff. In its Audit findings section press Add audit finding, fill in the form the same way (for example `Phishing simulation not run this quarter`, severity Low, status In progress) and press Add audit finding. The finding appears in the risk's Audit findings section; click its number to open its page, which shows the risk it concerns.
18. The seeded findings show the three states: on Multi-factor sign-in for remote access, "Contractor VPN accounts not removed when contracts end" is open and overdue; on the risk Unpatched firewall firmware, "Edge firewall firmware two releases behind" is risk accepted; on Encrypted backups with an offline copy, "Backup restore tests not recorded" is closed, with its closed date.
19. Sign out, and sign in as the Viewer, `viewer@acme.example`. Open Data intake: "You don’t have access to Data intake". The Viewer sees no evidence and no audit findings on the control and risk pages either (D50).
20. Sign out, and sign in as `risk.manager@globex.example`. Data intake lists only Globex's own files (`globex-cmdb-export.csv`, `globex-driver-device-standard.txt`, `globex-business-continuity-runbook.txt` and `globex-soc-tickets-2026-09.json`), none of Acme's. Assets shows Globex's own assets, with none of Acme's imported ones (no Order service, no Branch hypervisor (Leeds)). Paste the Acme finding's address from step 16: the page says "This record doesn't exist or you can't see it." The other org sees none of Acme's uploads, imports, evidence or findings.
21. Sign out. The generators: in a terminal on the Mac, from the repository root, run `pnpm gen:data --mode full --size tiny`. It sends its data through the real API at `https://grc.localhost` (its default `--base-url`), the way a customer's connector would: it creates its own orgs (`gen-1-1`, …), and for each prints the mappings it saved, the asset batches it pushed and the documents it uploaded, then where it wrote the answer key (`data/generated/1-tiny/`). Its API keys are revoked when it ends. Run it again: every batch and document comes back as a repeat, and nothing new is added. Signed in as `admin@acme.example`, Data intake's Sample data part shows these same commands to copy.
22. Press Sign out.
