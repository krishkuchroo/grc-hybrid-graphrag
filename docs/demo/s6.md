# S6 demo: search and chat

The click-through for S6's part of the checkpoint (D114, D182). Follow these steps while recording
the walkthrough with the Mac's screen recorder (D115).

## Before you start

- The one-time setup is done (D65): Caddy's local certificate is trusted, and the hosts file has
  `127.0.0.1 grc.localhost`.
- **The running stack shows S6 only after the MVP-end rebuild and migration (D229).** Until then
  https://grc.localhost runs the older code, with no Ask button in the header and no search or chat
  routes, and the database lacks the processing, review and chat migrations. Run this walkthrough
  once the migrations are applied and the stack is rebuilt:
  `docker compose -f packages/infra/compose.yaml --env-file .env up -d --build`.
- The GRC DBMS is running in Neo4j Desktop, and the stack is up, the worker included: it embeds the
  demo documents' passages and has Gemma read them.
- Ollama is running on the Mac with its two models: in a terminal, run `ollama serve` (or
  `brew services start ollama` to keep it running) and leave it open; `ollama list` shows
  `gemma4:12b` and `bge-m3`. Every answer, and every search, needs it: bge-m3 turns the question
  into a vector, and Gemma writes the graph query and the answer. Nothing leaves the Mac (D19).
- bge-m3's tokenizer file is set up once on the Mac: `pnpm --filter api setup:tokenizer`. The seed
  reads the demo documents into passages the way the worker does, and needs it. Without it the seed
  names this command, and reads them on its next run.
- The demo logins and data exist. They come from `pnpm seed:demo`, which creates two orgs, Acme
  Corp (`@acme.example`) and Globex Ltd (`@globex.example`), with one user per role and each org's
  own records, links, mappings, uploads, evidence, audit findings and review findings
  (`docs/demo/s1.md` to `s5.md`). For S6 it also makes sure that every demo document it uploads is
  read into passages (chunks): the two policy documents and the SOC ticket file of each org,
  including the Confidential ones (Acme's Incident Response Plan, Globex's Business Continuity
  Runbook). It calls neither Gemma nor bge-m3 (D82): the worker embeds the passages once Ollama is
  up. Running it again adds nothing. Every question below is answered from what it puts there.
- If you ran the S5 walkthrough's step 9, Acme's SOC ticket file reads Removed: its passage is never
  searched again (D52.5), and question 5 below is answered from the incident records alone.
- Every demo login uses the same password: the `DEMO_USER_PASSWORD` value in `.env`. It is never
  written here or printed.
- Have an authenticator app on your phone ready. The first sign-in of each login asks you to set up
  two-factor sign-in, as in the M0 demo (`docs/demo/m0.md`, steps 3 to 6).
- Gemma writes the graph query and the answer itself. With the same data they come out the same
  each time, but its words, and now and then which sources an answer cites, can differ a little
  from those below. What a person may not see never appears: it is left out before anything reaches
  Gemma (D23).

## Steps

1. Open https://grc.localhost and sign in as the Risk Manager, `risk.manager@acme.example`, with the demo password. In the left navigation, under Data, open Data intake. The demo documents `acme-acceptable-use-standard.txt` (Internal), `acme-incident-response-plan.txt` (Confidential) and `acme-soc-tickets-2026-09.json` (Internal) read Processed: the worker has embedded their passages with bge-m3 and Gemma has read them. Right after the seed they read Processing for a few minutes, while Gemma reads one passage at a time; wait until all three read Processed before you ask (Removed for the SOC ticket file if you ran the S5 walkthrough's step 9). The asset list `acme-cmdb-export.csv` reads Imported: asset lists are imported, never searched as passages.
2. Press Ask in the header. The chat panel opens on the right, over the screen, with "Ask about your risk data". It stays open while you move between screens, and closes with its close button or Esc.
3. Ask A1, the two-hop graph question: type it in the box ("Ask about your risk data") and press Enter. While it works, the steps tick off: Searching documents, Querying the graph (with the number of sources found), Writing the answer, then the answer streams in, word by word. It names the risk Ransomware on production servers and the two controls that mitigate it, Endpoint detection and response and Encrypted backups with an offline copy. Each source number in the answer is a chip: the teal ones are records the graph query found. Hover one to see its number, kind and name; click it to open the record's page beside the panel. Under the answer, Sources lists every source the answer cites, by number.
4. Open "How this answer was found" under the answer. Search reads Documents and graph. Graph query shows the read-only query Gemma wrote, in monospace, for example a path from the asset through EXPOSED_TO to its risks and through MITIGATED_BY to their controls: it ran in Acme's own database only, as the Risk Manager's read-only account, stopped after 5 s at most (D22, D52). Used counts the records and passages the answer cites, and Times shows how long it waited for its turn, found its sources, took to its first words, and in all.
5. Ask A2, answered by a policy document. The answer says a lost or stolen device is reported to the service desk within one hour, from section 4.3 of the Acceptable Use Standard. Its chip is parchment-coloured: a passage, found by vector search. Click it: the passage's own words show, with its document's name and kind, and Show the document in Data intake. (If you uploaded the Remote Working Policy in the S3 walkthrough, it says the same in its section 3.2 and may be cited too.)
6. Ask A3, which needs both kinds of source. The answer names the controls that mitigate Phishing of staff, Security awareness training and Multi-factor sign-in for remote access, as graph records, and from the Acceptable Use Standard's passage that every account belongs to one person, that remote access requires multi-factor sign-in, and that passwords are at least 12 characters. Records and passages are ranked together (RRF, k=60): a passage that names a record the graph found counts for both.
7. Ask A4, the framework question. The answer lists the requirements the control satisfies, one per framework: IA-2 (NIST SP 800-53), PR.AA-03 (NIST Cybersecurity Framework), A.8.5 (ISO/IEC 27001) and CC6.1 (SOC 2), the mappings of the S2 demo. Click a requirement's chip to open its page.
8. Ask A5, the incident question. The answer names the incident Ransomware attempt blocked on the build server (Confidential), which impacted the Build server, and the SOC ticket file's passage on ticket SOC-4471, ransomware behaviour blocked by endpoint detection on the build server on 3 September 2026. Only roles that view incidents ever get these (D50).
9. Ask A6, about a Confidential document. The answer quotes the Incident Response Plan: the on-call security analyst triages every alert within 30 minutes, and High means a production system compromised or ransomware detected on any device. The plan is Confidential: only people cleared for Confidential get it (D51). The answer is saved with that label, the highest of its sources, so a person whose clearance later drops below it sees only the question (S6-Q9). If a graph query ever fails, the answer still comes, with "The graph search didn't work this time, so this answer uses documents only." above it, and How this answer was found says why (D45.7).
10. Press Conversations (the clock icon) in the panel's header. The conversation is listed, named by the first 80 characters of its first question, with when it was last used. Conversations are each person's own; open it to come back to the answers.
11. Sign out, and sign in as the Control Owner, `control.owner@acme.example`. Press Ask: their conversation list is empty, none of the Risk Manager's. Ask A1 to A6 in turn. They get fewer sources:
    - A1: never the cluster, its risk or its controls. The cluster and the risk are Confidential, above their Internal clearance, and a search never gives a Control Owner a control, not even one they own: the graph account can't know who owns what, so it leaves controls out (their own controls are on the Controls screen).
    - A2: the same answer as the Risk Manager's, from the Acceptable Use Standard (Internal, a policy document their role reads).
    - A3: at most the risk Phishing of staff and the standard's passage on signing in; never a control.
    - A4: never the control or its mappings, for the same reason.
    - A5: never an incident and never the SOC ticket file: their role doesn't view incidents (D50). At most the Build server itself.
    - A6: never the Incident Response Plan: it is Confidential. The answer says what it can't find.
12. Sign out, and sign in as the Viewer, `viewer@acme.example`, cleared for Public only. Ask A1 to A6. A1, A2, A4, A5 and A6 normally each answer "I couldn't find anything about that in what you can see.", without asking Gemma for an answer: every document is Internal or Confidential, the cluster, the control of A4 and the framework catalogs are above Public, and Viewers don't view incidents. A3 names only what is Public: the risk Phishing of staff and Security awareness training, with no Multi-factor sign-in control (Internal) and no passage of the standard (Internal).
13. Sign out, and sign in as `risk.manager@globex.example`. Press Ask: none of Acme's conversations are listed. Ask A3. No Acme record, number or document appears anywhere in the answer, its Sources or How this answer was found: the passages searched are Globex's own, and the graph query runs only in Globex's own database (the org wall, D4, D22). Then ask G1 to G6, answered from Globex's own data:
    - G1: the risk Warehouse system outage in peak season, mitigated by Warehouse failover site and Uptime monitoring and alerting;
    - G2: every scanner is enrolled in mobile device management before it leaves the depot, and one that isn't can't sign in to the warehouse management system (the Driver Device Standard, sections 2.1 and 2.2);
    - G3: the control Mobile device management for scanners, and from the standard: report a lost scanner to the depot supervisor straight away, and the device team locks and wipes it remotely within one hour;
    - G4: IA-2 and AC-17 (NIST SP 800-53), PR.AA-03, A.8.5 and CC6.1;
    - G5: the incident Suspicious VPN sign-ins from abroad (Confidential), which impacted the VPN gateway, and the SOC ticket file's passage on GSOC-0912, sign-ins for one driver account from two countries within an hour;
    - G6: from the Business Continuity Runbook (Confidential): the duty manager declares a continuity event, operations switch to the warehouse failover site, drivers keep scanning and their scans queue on the device, and customers see a status note on the tracking page.
14. Two people at once. Open a private window (Safari: File, New Private Window; Chrome: File, New Incognito Window) and sign in there as `risk.manager@acme.example`; keep the Globex Risk Manager in the first window. Press Ask in both. In the private window, ask A1. As soon as it reads Searching documents, ask G6 in the first window: it shows "You're number 1 in the queue" and "Questions are answered one at a time." There is one Gemma for everyone, so questions take turns, and each holds its turn for both of its Gemma steps, the graph query and the answer (D48); nothing else is shared between the orgs. When the Acme answer starts streaming, press Stop in the private window: it ends at once with the words written so far and a Stopped tag, and is saved that way in the conversation. The first window moves on straight away: Searching documents, Querying the graph, then its answer. Close the private window.
15. The search API, for the benchmark's baseline. Vector mode (passages only, no Gemma) is what the S8 benchmark compares hybrid search against (D46); the chat panel always uses hybrid (S6-Q3), so vector mode is reached through `POST /api/v1/search` with an API key. In the first window, sign out, and sign in as the Admin, `admin@acme.example`. Open the browser's developer console (Safari: Develop, Show JavaScript Console, once Show features for web developers is on in Safari's Advanced settings; Chrome: View, Developer, JavaScript Console, where you may first be asked to type `allow pasting`) and run this, which makes a key for the Risk Manager's role and clearance that expires in a day, and copies it to the clipboard without showing it (D54):

    ```js
    const made = await (
      await fetch('/api/v1/api-keys', {
        method: 'POST',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify({
          name: 'S6 search demo',
          role: 'risk_manager',
          clearance: 'confidential',
          expiresAt: new Date(Date.now() + 24 * 60 * 60 * 1000).toISOString(),
        }),
      })
    ).json();
    copy(made.key);
    made.id;
    ```

16. In a terminal on the Mac, at the repository root, keep the key out of sight and out of the shell history: run `read -rs GRC_KEY`, paste the key and press Enter (nothing is shown). Then save Caddy's local root certificate for curl, and define a short helper that sends one search and lists its results:

    ```sh
    docker exec grc-caddy cat /data/caddy/pki/authorities/local/root.crt > "$TMPDIR/grc-caddy-root.crt"
    grc_search() {
      curl -sS --cacert "$TMPDIR/grc-caddy-root.crt" https://grc.localhost/api/v1/search \
        -H "Authorization: Bearer $GRC_KEY" -H 'content-type: application/json' \
        -d "{\"mode\": \"$1\", \"query\": \"$2\"}" |
        node -e '
          const a = JSON.parse(require("fs").readFileSync(0, "utf8"));
          if (a.error) { console.log(a.error.code + ": " + a.error.message); process.exit(1); }
          console.log("mode " + a.mode + ", graph query ran: " + a.graph.ran +
            (a.graph.fallback ? " (" + a.graph.fallback + ")" : ""));
          for (const r of a.results)
            console.log(r.rank + ". found by " + r.foundBy.join(" + ") + ": " +
              (r.type === "record" ? r.record.number + " " + r.record.name : "passage of " + r.passage.documentName));
        '
    }
    ```

17. Run the same question in each mode:

    ```sh
    grc_search vector 'Which risks is the Core web cluster exposed to, and which controls mitigate them?'
    grc_search hybrid 'Which risks is the Core web cluster exposed to, and which controls mitigate them?'
    ```

    Vector mode reads "graph query ran: false" and lists only passages, each found by vector: Gemma isn't asked at all. Hybrid mode reads "graph query ran: true" and lists the Core web cluster, Ransomware on production servers, Endpoint detection and response and Encrypted backups with an offline copy, found by graph, ranked together with the passages; a passage that names one of those records reads "found by vector + graph". The key sees what a Risk Manager at Confidential sees, of Acme only (D230). Searches aren't audited; questions are (S6-Q7).

18. Revoke the key. Back in the browser console, run `await fetch('/api/v1/api-keys/' + made.id, { method: 'DELETE' })`: its status is 204. In the terminal, `grc_search vector 'Which risks is the Core web cluster exposed to?'` is now refused: the key no longer works. Run `unset GRC_KEY`.
19. Press Sign out.
