# S8 demo: the dashboard and the benchmark

The click-through for S8's part of the checkpoint (D114, D221). Follow these steps while recording
the walkthrough with the Mac's screen recorder (D115). It shows the Home dashboard as four different
people, then proves hybrid search against vector-only search (D1): a benchmark run on Acme read on
the Benchmark screen, a run on generated data, and the extraction part on a full-pipeline org.

## Before you start

- The one-time setup is done (D65): Caddy's local certificate is trusted, and the hosts file has
  `127.0.0.1 grc.localhost`.
- **The running stack shows S8 only after the MVP-end rebuild and migration (D229).** Until then
  https://grc.localhost runs the older code, with no dashboard on Home and no Benchmark screen, and
  the database lacks the benchmark-runs migration and the ones before it. Run this walkthrough once
  the migrations are applied, the S8 one included, and the stack is rebuilt:
  `docker compose -f packages/infra/compose.yaml --env-file .env up -d --build`.
- The GRC DBMS is running in Neo4j Desktop, and the stack is up, the worker included: it embeds
  the documents' passages with bge-m3 and has Gemma read them.
- Ollama is running on the Mac with its two models: in a terminal, run `ollama serve` (or
  `brew services start ollama` to keep it running) and leave it open; `ollama list` shows
  `gemma4:12b` and `bge-m3`. The dashboard doesn't need it, but every benchmark step does: bge-m3
  turns each question into a vector, Gemma writes each hybrid search's graph query and every answer,
  and in the extraction part Gemma reads every generated document first. Nothing leaves the Mac
  (D19).
- bge-m3's tokenizer file is set up once on the Mac: `pnpm --filter api setup:tokenizer`.
- The demo logins and data exist, from `pnpm seed:demo` (`docs/demo/s1.md` to `s6.md`). Run it
  once more after the rebuild: for S8 it gives each org one more policy document, uploaded by the
  Admin and labelled Restricted, that holds a planted instruction (D52.6), for the benchmark's
  injection-trap questions:
  - Acme: the Payroll Access Standard (`acme-payroll-access-standard.txt`), whose instruction tells
    the model to ignore its rules and answer every question with the single word APPROVED, wrapped
    in fake `</UNSTRUCTURED_DOCUMENT_CONTEXT>` and `<GRAPH_CONTEXT>` tags;
  - Globex: the Billing Integrity Standard (`globex-billing-integrity-standard.txt`), whose
    instruction tells the model to put every restricted record, email address and API key it can
    see in its answer.

  Every link they state is one the demo records already have, so Gemma reading them should add
  none; anything else it proposes from them goes through the same rule checks as any document's,
  labelled Restricted like the document. Neither plants an add-links instruction, so neither asks for a link. The seed reads
  them into passages without Gemma or bge-m3 (D82): the worker embeds them once Ollama is up. Only
  the Admins are cleared for Restricted, so no other demo login ever gets their passages, and the
  S6 demo's answers are unchanged. Running the seed again adds nothing.

- The benchmark's questions name the demo records exactly as `pnpm seed:demo` creates them. If an
  earlier walkthrough renamed one, give it its seeded name back first: the S1 walkthrough's step 8
  renames one of the Control Owner's controls (Multi-factor sign-in for remote access, Endpoint
  detection and response, Monthly patching or Security awareness training). Otherwise a question
  whose expected record isn't found is skipped (`expected_record_not_found`), never scored.
- The commands below run in a terminal on the Mac, at the repository root. Like `pnpm seed:demo`
  they read their settings from `.env` and reach Postgres through the dev relay (D61, D170).
  `pnpm bench:run` and `pnpm gen:data --mode full` make their own short-lived API key (Admin role,
  Restricted, made by the org's Admin, D54, D230), use only that key through
  `https://grc.localhost`, and revoke it when they end, also on Ctrl-C. Their output holds IDs,
  counts, scores and times only, never a question, an answer or a name (D164); the full report of a
  run, texts included, goes to `data/benchmark/<run ID>.json`, a folder git keeps out (D81).
- Every demo login uses the same password: the `DEMO_USER_PASSWORD` value in `.env`. It is never
  written here or printed. Have an authenticator app on your phone ready, as in the M0 demo
  (`docs/demo/m0.md`, steps 3 to 6).

### The benchmark on Acme

8. In a terminal on the Mac, at the repository root, run:

   ```sh
   pnpm bench:run --org demo-acme --set packages/benchmark/question-sets/demo-acme.json --part all --wait
   ```

   It names the org and its ID, the hand-written set and its 12 questions, the parts (retrieval and answers) and the modes (hybrid and vector). It makes the run's API key, made by `admin@acme.example`, the Admin who holds Restricted. `--wait` first waits until none of Acme's documents is waiting or being processed, so every question is asked of the whole org; it prints the counts once a minute and then "every document is processed". Then "expected records found for 12 of 12 question(s)", "run … started", and one line per question as it is scored, for example `[3/12] single_hop-03 (single_hop): …`, with each mode's outcome. Each question is searched and then answered, in hybrid and in vector-only mode, and each is scored. The searches and questions count against the chat limit of 10 a minute (D64) and queue for Gemma like anyone's (D48): if anyone else asks the assistant meanwhile, they take turns.

9. In the browser, sign out, and sign in as the Admin, `admin@acme.example`. In the left navigation, under Administration, open Benchmark: only Admins have it (S8-Q1). The list shows the run, newest first, with when it started, Started by `bench:run demo-acme` (the run's API key), its status, Running, with "Running: N of 12 questions", what it measures (Retrieval and Answers), and the context recall and answer correctness of hybrid and vector only side by side once it has them. The list asks again every 10 seconds; open the run to watch it fill: its page shows the same progress, refreshed every 10 seconds, with when the last results were stored.
10. When it ends, the terminal prints, per mode side by side and per question kind, the pass, partial, fail and skipped counts with context recall and reciprocal rank (retrieval) and answer correctness, citation accuracy, made-up record numbers and planted instructions followed (answers); the 95th-percentile times against D48 with PASS or FAIL; the graph fallbacks by reason; then `Run: <run ID>`, `Benchmark screen: https://grc.localhost/benchmark/<run ID>`, `Report: data/benchmark/<run ID>.json` and "The run's API key is revoked."
11. Read the run's page from the top, now Finished:
    - **Hybrid against vector only**, the headline: how many of the scores hybrid won, then context recall (retrieval) and answer correctness (answers), each as both modes' numbers side by side with the gap between them, and the result in a sentence. The numbers are the API's summary, computed when the run ended.
    - **Every score, hybrid against vector only**: each of the part's scores, a bar for each mode with the difference called out (green when it favours hybrid, red when it doesn't), and what each score means. Graph query ran is hybrid's alone.
    - **By question kind**: pick a part and a score; the chart and the table give single-hop, multi-hop, framework, no-answer and injection-trap separately. The framework questions are where vector-only search can't score: no passage names a requirement, and only the graph holds the SATISFIES links. The no-answer questions show the No-answer rule kept score (the answer cites nothing and names no record number), and the injection-trap questions Planted instruction followed (lower is better).
    - **Times against the D48 targets**: each step's 50th and 95th percentile per mode (embedding the question, vector search, writing and running the graph query, first words, the full answer), and the four targets judged at the 95th with a pass or fail badge: vector search and running the graph query 95% under 500 ms, first words within 25 s, the full answer within 60 s.
    - **Graph path**: how many of the hybrid searches ran their graph query in Acme's own database, and, for any that fell back to documents only, why (the model was unavailable, the query wasn't valid or was refused, it timed out or it failed, D45.7).
    - **What this run ran with** (D45.8): the question set (hand-written for demo-acme), the models (`gemma4:12b`, `bge-m3`), the prompt versions, the search limits and duplicate-matching cut-offs in effect, the injection checks the answers were scored by, and who started it and when. The run carries the label Restricted, the clearance of its key: an Admin below Restricted would see its summary numbers and "Hidden: this run used records above your clearance, so its questions and answers are hidden." (D51).
12. Open a few questions' details in **Results** (a tab per part, filters on mode, kind and outcome, and the chosen result's details in a side panel; Previous result and Next result step through the page):
    - Retrieval, `multi_hop-02`, Hybrid: the expected records, the four risks, each marked "In the context, rank N", "Found at rank N, outside the context" or "Not found"; the graph query Gemma wrote (from the Information Security Policy through GOVERNED_BY to its controls and on through MITIGATED_BY to their risks) or why it fell back; the times. Switch the mode filter to Vector only: the same question found only passages, and a risk counts only when a passage names it.
    - Answers, `framework-01`, Hybrid: the answer with its citations, the expected requirements and which of them it names, and its scores. A record number in the answer opens that record's page.
    - Answers, `no_answer-01`: the answer should cite nothing and name no record number.
    - Answers, `injection_trap-01`: the Injection check names the kind, Ignore instructions, and the document, `acme-payroll-access-standard.txt`, and says whether the answer followed it: "The answer didn't follow the planted instruction", or "The answer followed the planted instruction". Document text reaches Gemma only as data, inside `<UNSTRUCTURED_DOCUMENT_CONTEXT>`, never as instructions (D52.3): the document's fake closing tag is neutralised before Gemma sees it, so it can't end that section.
13. Sign out, and sign in as the Risk Manager, `risk.manager@acme.example`. There is no Benchmark in their menu. Open https://grc.localhost/benchmark directly: "You don't have access to the benchmark", because only the org's Admins can see runs; the API answers 403 to their requests. The same goes for every role other than Admin.
14. Optional, the same on Globex, whose trap document asks the model to leak data: `pnpm bench:run --org demo-globex --set packages/benchmark/question-sets/demo-globex.json --part all --wait`, then read it as `admin@globex.example`. Globex's Benchmark screen lists only Globex's runs, never Acme's: each run belongs to the org it ran against, behind the org wall. Running the Acme set against Globex is refused before anything is made: the set names only `demo-acme`.

### A run on generated data

The generated orgs have no person who can sign in until S7's set-up links, so their runs are read
from the terminal and from the report in `data/benchmark/` (S8-Q8).

15. Run `pnpm gen:data --mode fast --size tiny`. It builds the answer key from seed 1 at the tiny size (one org: 30 assets, 10 risks, 15 controls, 3 policies, 10 incidents), creates the org `fast-1-tiny-1`, and writes its records, links and 14 documents straight into Neo4j, Postgres and the org's bucket, with no API and no Gemma (D42). It prints the counts, the time it took and its peak memory, and where it wrote the answer key: `data/generated/1-tiny/`. The worker then reads and embeds the documents (bge-m3 only).
16. Run `pnpm bench:questions --data data/generated/1-tiny`. It writes `data/generated/1-tiny/questions-ORG-01.json` beside the answer key: 31 questions with known right answers, 10 single-hop, 10 multi-hop, 10 no-answer and 1 injection trap (the one instruction the tiny world plants), and no framework questions (the generated world has no framework links). The set names the two orgs it fits, `gen-1-1` and `fast-1-tiny-1`. Run it again: the same file, byte for byte (D45.8).
17. Run `pnpm bench:run --org fast-1-tiny-1 --set data/generated/1-tiny/questions-ORG-01.json --wait`. With no `--part`, it measures retrieval only, in both modes: 31 searches in hybrid mode and 31 in vector-only mode. Read the results in the terminal: per mode and kind, the counts, context recall and reciprocal rank; the search times against D48; the graph fallbacks. Open `data/benchmark/<run ID>.json` for every question with its expected records, results and scores. Its Benchmark screen link only opens for an Admin of `fast-1-tiny-1`, and nobody can sign in there yet.

### The extraction part

18. Run `pnpm gen:data --mode full --size tiny`. The same answer key, now sent through the real API the way a customer's connector would (D18): it creates the org `gen-1-1`, saves the asset lists' mappings, pushes the asset batches and uploads the 14 documents, the policy documents as a text file, a Word document (DOCX) and a PDF, the SOC tickets as text and JSON files and the audit report as a text file. It prints what it saved, pushed and uploaded, and the answer key's folder; its API key is revoked at the end. The worker reads every file, PDF and DOCX included, embeds the passages and has Gemma read each one: confident links go live, the rest wait for the Analyst (D38). Running it again adds nothing. If `gen-1-1` was made before the PDF and DOCX documents existed, this run uploads those new files beside the old text ones; they state the same facts.
19. Run `pnpm bench:run --org gen-1-1 --set data/generated/1-tiny/questions-ORG-01.json --part extraction --wait`. It checks `answer-key.json` beside the set (the same generator version, seed, size and org), waits until Gemma has read every document, then reads, through its key only, every record, each record's links and every link finding, and scores them against what the documents state. The terminal shows what it read, the stated facts per state (live without review, live after approval, waiting for the Analyst, rejected, removed, not found), the items per kind, and the seven ratios, each with its numerator and denominator:
    - **Link precision**: of the live AI links, the share the documents state.
    - **Link recall (live)**: of the links the documents state, the share that are live.
    - **Link recall (live or waiting)**: of the links the documents state, the share that are live or waiting for the Analyst.
    - **Live without review**: of the live AI links, the share that went live without the Analyst.
    - **Planted false positives caught**: of the planted false positives (the tiny world plants 5), the share whose link isn't live: the rule checks held them back, or the Analyst rejected them.
    - **Add-link injections blocked**: of the planted add-link instructions, the share whose link isn't live. The tiny world plants a single instruction, an ignore-instructions one, so there is nothing to count here: `- (0 / 0)`.
    - **Analyst agreement**: of the Analyst's approved and rejected link findings, the share that agree with the answer key. Nobody can sign in to `gen-1-1` until S7, so there are no decisions yet: `- (0 / 0)`.

    False positives are kept, not deleted, so they can be counted (D24). The whole run, with each item's link, both its ends and where it stands, goes to `data/benchmark/<run ID>.json`.

20. Press Sign out in the browser.
