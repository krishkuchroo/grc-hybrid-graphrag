# S2 demo: frameworks and mappings

The click-through for S2's part of the checkpoint (D114, D182). Follow these steps while recording
the walkthrough with the Mac's screen recorder (D115).

## Before you start

- The one-time setup is done (D65): Caddy's local certificate is trusted, and the hosts file has
  `127.0.0.1 grc.localhost`.
- The stack is running: `docker compose -f packages/infra/compose.yaml --env-file .env up -d`.
- The demo logins, records, catalogs and mappings exist. They come from `pnpm seed:demo`, which
  creates two orgs, Acme Corp (`@acme.example`) and Globex Ltd (`@globex.example`), with one user
  per role and each org's own records (as in the S1 demo, `docs/demo/s1.md`). It also loads the
  four framework catalogs into each org (NIST SP 800-53, the NIST Cybersecurity Framework, ISO/IEC
  27001 and SOC 2, with NIST's own links between them) and adds each org's fixed set of about 25
  mappings: which of its controls satisfies which requirement. The two orgs' mappings differ. It
  prints the login list. Running it again adds nothing.
- Every demo login uses the same password: the `DEMO_USER_PASSWORD` value in `.env`. It is never
  written here or printed.
- Have an authenticator app on your phone ready. The first sign-in of each login asks you to set up
  two-factor sign-in, as in the M0 demo (`docs/demo/m0.md`, steps 3 to 6).

The logins used below:

| Login                               | Role               | Clearance    |
| ----------------------------------- | ------------------ | ------------ |
| `compliance.manager@acme.example`   | Compliance Manager | confidential |
| `control.owner@acme.example`        | Control Owner      | internal     |
| `auditor@acme.example`              | Auditor            | confidential |
| `viewer@acme.example`               | Viewer             | public       |
| `compliance.manager@globex.example` | Compliance Manager | confidential |

The coverage figures below are those of a fresh `pnpm seed:demo`, seen by the Compliance Manager.
Coverage only ever counts the active controls the signed-in person can see, so other logins see
other figures.

## Steps

1. Open https://grc.localhost and sign in as the Compliance Manager, `compliance.manager@acme.example`, with the demo password.
2. In the left navigation, open Frameworks. It lists the four frameworks: NIST SP 800-53 (Rev. 5), NIST Cybersecurity Framework (2.0), ISO/IEC 27001 (2022) and SOC 2 Trust Services Criteria. Each shows its version, its publisher, its number of requirements and its coverage: a bar and a line such as "4 of 61 requirements covered, 3 implemented". A requirement is covered when an active control you can see satisfies it, and implemented when one of those controls is implemented.
3. Open SOC 2 Trust Services Criteria. The coverage panel at the top reads 4 of 61 requirements covered, 3 implemented. In the requirements list, set Coverage to Not covered: the list keeps only the criteria that no control you can see satisfies, CC6.6 Protection at the system boundary among them. Set Coverage back to Any coverage.
4. Go back to Frameworks and open NIST Cybersecurity Framework. Type `PR.AA-03` in Search and open the CSF subcategory PR.AA-03, "Users, services, and hardware are authenticated". Under "Controls that satisfy this requirement" is Acme's Multi-factor sign-in for remote access. Under "Related requirements in other frameworks", "PR.AA-03 maps to" lists the NIST SP 800-53 controls NIST itself links it to, IA-2 and IA-5 among them.
5. Click IA-2 to open the 800-53 control IA-2, Identification and Authentication (Organizational Users). The same Acme control satisfies it. Its related requirements show both ways: "IA-2 maps to" lists its ISO links, the ISO/IEC 27001 control A.5.16 Identity management, and "Mapped to IA-2" lists the CSF subcategories PR.AA-01 and PR.AA-03. Click A.5.16 to open the ISO control. These links come from NIST's own crosswalks and can't be changed in the app.
6. Now map a control to a SOC 2 criterion as the Compliance Manager. Open Frameworks, then SOC 2 Trust Services Criteria, set Coverage to Not covered, type `CC6.6` in Search and open CC6.6 Protection at the system boundary. Its "Related requirements in other frameworks" is empty: only NIST's own mappings are loaded and they don't cover SOC 2. SOC 2's links to other frameworks come later, suggested by the AI in S4 and approved through the Analyst's review in S5 (D212 (4)).
7. On CC6.6, under "Controls that satisfy this requirement", press Map a control. Type `firewall`, pick Web application firewall and press Map control. The control appears under "Controls that satisfy this requirement", a message says it now satisfies CC6.6, and the Coverage panel reads Implemented.
8. Go back to SOC 2 Trust Services Criteria: its coverage now reads 5 of 61 requirements covered, 4 implemented, one more than before.
9. Open CC6.6 again and press Remove next to Web application firewall, then Remove mapping in the confirmation. The control is gone from the list. Back on SOC 2 Trust Services Criteria, the coverage is again 4 of 61 requirements covered, 3 implemented. The audit trail keeps both changes, with your name.
10. Open Controls in the left navigation, then Multi-factor sign-in for remote access. Its "Requirements this control satisfies" section lists the control's requirements, one group per framework: IA-2 (NIST SP 800-53), PR.AA-03 (NIST Cybersecurity Framework), A.8.5 (ISO/IEC 27001) and CC6.1 (SOC 2), each linking to its requirement's page. Its Source note field reads "NIST 800-53": free text about where the control comes from, not a mapping. Coverage, the Frameworks screen and this requirements section never read the Source note (D212 (5)); only the requirements mapped to the control count.
11. Sign out, and sign in as the Control Owner, `control.owner@acme.example`. Open Controls, then Multi-factor sign-in for remote access, one of the controls they own. They see the same "Requirements this control satisfies" list, but with no Add requirement button and no Remove button: only Admins and Compliance Managers map controls to requirements, even on a control the person owns (D212 (3)). Click IA-2: the requirement page shows their control with no Map a control button and no Remove button. On Frameworks, a note says coverage counts only the controls they own.
12. Sign out, and sign in as the Auditor, `auditor@acme.example`. Frameworks, the coverage, the requirement pages and each control's "Requirements this control satisfies" all show, with no Map a control, Add requirement or Remove button anywhere: everyone other than Admins and Compliance Managers reads the mappings without changing them (D212 (3)).
13. Sign out, and sign in as the Viewer, `viewer@acme.example`. The Viewer can't change mappings either: there is no Map a control, Add requirement or Remove button. The catalogs carry the internal label and the Viewer's clearance is public, so Frameworks has no catalogs to list for them, and a control's page shows no requirements: labels apply to the catalogs as to every record (D51).
14. Sign out, and sign in again as the Compliance Manager, `compliance.manager@acme.example`. Open NIST SP 800-53, type `CP-9` in Search and open CP-9 System Backup: Acme's Encrypted backups with an offline copy satisfies it. Copy the page's address.
15. Sign out, and sign in as `compliance.manager@globex.example`. Frameworks shows the same four frameworks, with Globex's own coverage figures. Paste the CP-9 address: the requirement opens, because every org has its own copy of the catalogs, but it says "No control you can see satisfies this requirement." The other org sees none of Acme's controls or mappings.
16. Press Sign out.
